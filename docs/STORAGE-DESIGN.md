# Storage Design

How MEGA persists a saved dice-rolling session, and what deletion actually
does. Covers `org.mega.entropy.storage` (session data) and
`org.mega.entropy.security.pin` (the optional PIN).

## What gets saved, and when

Nothing is saved automatically. A session lives only in memory
(`DiceSessionViewModel`) until the user explicitly chooses to save it on
the Save screen, with three options:

- **Don't Save** — nothing is written to disk.
- **Save Dice Rolls** (default) — persists only the raw dice results.
- **Save Dice Rolls + Derived Mnemonic** — also persists the 24 words,
  gated behind a second, separate confirmation, since this increases the
  amount of sensitive data at rest.

Either way, every derived value (`X`, `E`, the checksum, the words) is
recomputed from the saved dice rolls when a session is reopened — nothing
about *how* the mnemonic was derived is stored, only the raw rolls (and,
optionally, the resulting words themselves).

## Where it lives

App-private internal storage only: `context.filesDir/mega_sessions/`. MEGA
never uses external/shared storage and never requests a storage permission.

Per session, two files:

| File | Contents | Encrypted? |
|---|---|---|
| `<sessionId>.meta` | id, created-at timestamp, roll count, whether a mnemonic was saved, Keystore alias | No — none of this is sensitive on its own |
| `<sessionId>.enc` | AES-256-GCM ciphertext of the dice rolls (and mnemonic, if saved), with a 12-byte GCM IV prefixed | Yes |

`sessionId` is a random UUID (`java.util.UUID.randomUUID()`) — a storage
identifier only, generated *after* the mnemonic has already been derived,
with no path back into entropy derivation (see
[`docs/NO-RNG-PROOF.md`](NO-RNG-PROOF.md) §5).

Both files use a small, hand-rolled plain-text line format instead of a
JSON library, so the on-disk layout is directly readable in
`org.mega.entropy.storage.SessionSerializer` without any parsing
dependency. Example encrypted-payload plaintext (before AES-GCM encryption):

```
MEGA-SESSION-V1
ROLLS:1,4,3,6,2,...
MNEMONIC:word1 word2 word3 ... word24
```

(the `MNEMONIC:` line is present only when the mnemonic was also saved.)

## Encryption

- **Algorithm:** AES-256-GCM (`AES/GCM/NoPadding`), 128-bit authentication
  tag.
- **Key:** One dedicated Android Keystore key **per session**, alias
  `mega_session_<uuid>`. The key never leaves the Keystore — the app only
  ever obtains a `Cipher` handle that uses it, never the raw key bytes.
  Generated via `KeyGenParameterSpec` with `PURPOSE_ENCRYPT or
  PURPOSE_DECRYPT`, `BLOCK_MODE_GCM`, `ENCRYPTION_PADDING_NONE`, 256-bit
  key size (`SessionCrypto.getOrCreateSecretKey`).
- **IV:** A fresh IV is generated by the `Cipher` itself for every single
  encryption call (never manually constructed or reused), and stored
  alongside the ciphertext it belongs to (`SessionCrypto.encrypt`) — an IV
  isn't secret, but reusing one with the same key breaks GCM's security
  guarantees, so each encryption gets its own.
- **Decryption fails closed:** `SessionCrypto.decrypt` looks up the
  *existing* Keystore key for a session's alias and throws
  `IllegalStateException` if it's missing, rather than silently minting a
  new key that would just produce garbage plaintext. Authentication
  failures (`AEADBadTagException`, e.g. from a tampered or corrupted file)
  are left uncaught and propagate — MEGA never attempts to interpret
  partially- or incorrectly-decrypted data.

Storage cryptography and wallet entropy are completely independent: no
storage key is ever derived from dice rolls or a mnemonic, and
`org.mega.entropy.storage` never imports `org.mega.entropycore`.

## Deletion

**Delete Session** deletes, in order: the session's dedicated Keystore key
(`SessionCrypto.deleteKey`), then its `.meta` and `.enc` files
(`SessionFileStore.deleteSessionFiles`). **Delete All MEGA Data** does this
for every saved session.

Deleting the Keystore key matters as much as deleting the files: even if a
copy of the ciphertext somehow survived (a forensic recovery of "deleted"
flash storage, for example), it would be cryptographically inaccessible
without the destroyed key. MEGA does **not** claim to securely overwrite
flash storage — flash-memory wear-leveling means an app-level "secure
delete" of the ciphertext bytes themselves cannot promise the underlying
NAND cells are actually overwritten. Deletion here relies on app
sandboxing, the device's own filesystem encryption, and cryptographic key
destruction — not on an unverifiable overwrite claim.

## Backups

The manifest sets `android:allowBackup="false"` **and** modern
`android:dataExtractionRules` (excluding both cloud backup and
device-to-device transfer) **and** legacy `android:fullBackupContent` rules
— all three, since different Android versions and OEM backup agents
consult different mechanisms. See `app/src/main/AndroidManifest.xml` and
`app/src/main/res/xml/`.

## The optional MEGA PIN

Stored separately, under `context.filesDir/mega_security/` — see
`org.mega.entropy.security.pin`:

- `pin.record`: `salt` (16 random bytes), `hash` (32-byte
  `PBKDF2WithHmacSHA256` output, 120,000 iterations), iteration count, and
  a created-at timestamp. Plain text, **not** AES-GCM encrypted — unlike
  session payloads, a salted PBKDF2 hash is not the kind of secret that
  needs confidentiality at rest (an attacker with hash + salt still has to
  actually run the same brute-force they'd have to run against the same
  hash stored anywhere else); it's kept unencrypted for the same reason
  session *metadata* is unencrypted, avoiding a circular key-management
  problem for something that isn't the protected artifact itself.
- `pin.attempts`: failed-attempt counter and lockout expiry, for local
  rate-limiting (escalating lockout: 5 fails → 30s, 10 → 5 min, 15+ → 30
  min, capped — never permanent, and never affects saved session data).

The PIN is deliberately an **additional UI-level access barrier**, layered
on top of (not a replacement for) Android sandboxing and the AES-256-GCM
session encryption above. See
[`docs/SECURITY-MODEL.md`](SECURITY-MODEL.md) for why a 5–8 digit PIN isn't
treated as having meaningful cryptographic entropy on its own.
